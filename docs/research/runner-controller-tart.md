# Tart evidence for a one-job Rust runner controller

Researched 2026-11-07. This is research, not deployment or runtime validation. No VM host was accessed, no secrets were retrieved, and no GitHub/Tailscale/host state was changed. Existing Python policy/lifecycle tests in this repository are synthetic evidence only. The proposed Rust daemon should replace those unfinished Python components, retaining useful constraints as Rust policy and tests rather than layering a second controller on them.

## Recommendation and boundaries

**Design inference:** one local Rust daemon invoking the pinned Tart CLI is sufficient for the first M2 MacBook: one durable journal, one exclusive job slot, one digest-pinned macOS base, one disposable clone, bounded guest bootstrap/status transport, and stop/delete reconciliation. Orchard, a fleet scheduler, a separate host-side shell supervisor, and Linux support can wait. Keep the VM adapter narrow enough to add Linux and another Mac later. A separate small guest service can own the runner process so a lost host transport does not ambiguously restart a job.

The critical unproven requirement is **booting under non-admin `_runner` in the system launchd domain before any GUI login**. `--no-graphics` explicitly avoids a VM window, but does not establish that the Virtualization framework works in every service-account security context. Tart's own FAQ warns that macOS 15+ needs an unlocked login keychain and calls its automated terminal workaround potentially temporary. Do not represent the requirement as solved by a plist. [Pinned headless FAQ](https://github.com/openai/tart/blob/2.41.1/docs/faq.md), [headless run implementation](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Run.swift).

## Actual CLI contract

- `tart clone IMAGE@sha256:DIGEST LOCAL_NAME` accepts immutable OCI digest references. A missing cache image is pulled implicitly. A mutable tag is unsuitable for reproducible admission; cloning an already cached tag does not promise a registry refresh. `tart fqn IMAGE:TAG` resolves the cached reference to a digest but is a hidden command, so use it only in a reviewed image-update operation, not as the controller's runtime dependency. Do not pass `--overwrite`: a name collision should stop admission. [Clone](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Clone.swift), [reference parser](https://github.com/openai/tart/blob/2.41.1/Sources/tart/OCI/RemoteName.swift), [FQN](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/FQN.swift).
- `tart set NAME --cpu 4 --memory 8192` sizes a stopped guest; memory is MiB. `--disk-size` is GB and increases capacity; it is not a host writable-byte quota. [Set](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Set.swift).
- `tart run --no-graphics --no-clipboard --no-audio --no-usb-accessories --net-softnet ... NAME` is a **foreground, long-lived VM owner process**. There is no `run --detach` flag in this release. The Rust daemon should spawn and supervise it, drain bounded stdout/stderr, and retain its own durable VM identity. Shell `&` is not a supervisor. The process creates the VM control socket and waits in the headless application event loop until the VM exits. [Run](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Run.swift).
- Inventory is `tart list --source local --format json`, **not `--json`**. Fields are `Source`, `Name`, `Disk`, `Size`, `Accessed`, `Running`, and `State`; states distinguish running, stopped, suspended. Numeric size fields are human-unit conversions, not exact accounting or quota counters; disk capacity may be unavailable while a disk is open. `tart get NAME --format json` also exposes CPU, memory, disk format, MAC, and state. Pin schema fixtures to the selected version and reject malformed/unknown state when making admission decisions. [List](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/List.swift), [Get](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Get.swift), [size encoding](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Formatter/HumanReadableByteCount.swift).
- `tart ip --wait 120 NAME` defaults to host DHCP reservation/lease lookup. `--resolver=arp` is for bridged networking and does not work with Softnet; `--resolver=agent` uses the guest agent through the VM control socket. IP resolution is not guest readiness or runner readiness. [IP](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/IP.swift).
- `tart stop --timeout 30 NAME` finds the Tart owner PID through its file lock, sends SIGINT, waits, then uses SIGKILL. Despite its timeout help wording, do not assume this gives a macOS runner time for a cooperative job shutdown: the run implementation cancels VM execution on SIGINT; its separate SIGUSR2 request-stop path notes a macOS confirmation dialog. Signal/stop is cleanup, not a job-completion acknowledgment. `tart delete NAME` rejects a running VM. Recheck inventory after stop and before delete; treat already stopped/missing as idempotent cases at the adapter layer. [Stop](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Stop.swift), [Run](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Run.swift), [VM locks/deletion](https://github.com/openai/tart/blob/2.41.1/Sources/tart/VMDirectory.swift).

## Disk behavior and a 500 GB host

Ordinary cloning on APFS is copy-on-write: a clone initially shares physical blocks, while its guest writes allocate additional blocks. Logical disk size is therefore neither current host consumption nor a maximum incremental write budget. Guest deletion releases only blocks no other clone/cache still references. Base updates can temporarily require old base + new base + live clone + download/assembly space. Keep one current base and at most one candidate during a planned update; use a single-Xcode image rather than the multi-Xcode runner variant. [Clone behavior](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Clone.swift), [image variants](https://github.com/cirruslabs/macos-image-templates/blob/d6a3774b296fb80aa42c2a4885d6eb364a909ffd/README.md).

Tart 2.41.1 also has `clone --stacked`: a remote standalone macOS image remains an immutable base with a private ASIF writable overlay. This requires **macOS 27+ and a binary built with DiskImageKit support**; a host OS version alone does not prove the distributed binary supports it. It is an optional measured optimization, not necessary for initial APFS clones. Avoid deep overlay lineages. [Stack support guard](https://github.com/openai/tart/blob/2.41.1/Sources/tart/DiskImageStack.swift), [stacked clone implementation](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Clone.swift), [Apple DiskImageKit](https://developer.apple.com/documentation/diskimagekit).

`pull`/`clone` can automatically prune OCI/IPSW caches when space is insufficient; clone limits automatic reclaim to 100 GB by default. This is **not a 100 GB cache cap** and does not clean forgotten local job VMs. Explicit `tart prune --entries caches --space-budget N` or `--older-than N` uses LRU/age criteria; `--entries vms` also exists but is too broad for automatic cleanup of a mixed host. Prefer deleting exact controller-owned VM names after verified stop. [Prune source](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Prune.swift), [clone pruning](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Clone.swift).

**Initial sizing inference:** retain 4 vCPU / 8 GiB RAM and one guest on a 32 GiB M2; profile real Xcode builds before raising memory. The upstream base template uses 4 CPU / 8 GiB / 50 GB disk; the Xcode template currently defaults to a 140 GB virtual disk and checks for 15 GB free inside the guest. Actual published images must be inspected by digest. Existing 80 GiB host reserve + 60 GiB guest-write allowance is provisional admission arithmetic, not isolation or quota enforcement. A guest can write more than 60 GiB unless disk capacity/storage limits enforce it. Reserve against a defensible worst case for the selected image, monitor host free space while running, and stop before the host/service floor. Select an APFS quota/container arrangement only after proving its clone-sharing behavior and full-volume failure recovery; do not promise per-VM quotas Tart does not implement. [Base sizes](https://github.com/cirruslabs/macos-image-templates/blob/d6a3774b296fb80aa42c2a4885d6eb364a909ffd/templates/base.pkr.hcl), [Xcode sizes](https://github.com/cirruslabs/macos-image-templates/blob/d6a3774b296fb80aa42c2a4885d6eb364a909ffd/templates/xcode.pkr.hcl).

## Bootstrap and completion across controller restarts

SSH works with `tart ip`, but adds IP readiness, host-key policy, guest credentials, and local TCP access. Stock images use public `admin`/`admin` credentials; never treat these as a secret or an isolation boundary. Avoid `sshpass` and disabled host-key checking in a persistent controller. A derived image could install a dedicated bootstrap key and restrict SSH, but that key becomes another lifecycle responsibility. [Official SSH guidance](https://tart.run/quick-start/#ssh-access).

**Preferred first proof:** the non-vanilla base/Xcode images include Tart Guest Agent; `tart exec -i NAME /path/to/fixed-bootstrap` can send a bounded input payload over the VM control socket/vsock without an IP route or SSH password. Tart 2.41.1 requires macOS 14+ for exec. The agent's standard image configuration runs RPC in a **guest LaunchAgent**, so it relies on a logged-in guest session; its guest LaunchDaemon only handles resize by default. Host no-GUI-login and guest auto-login are different requirements. An image can instead run RPC as a guest daemon, but then commands run as root unless explicitly arranged otherwise. Verify the intended guest identity and exact image behavior. [Exec](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Exec.swift), [guest agent components](https://github.com/openai/tart-guest-agent/blob/6d4bd9c74ebbbc83d10ac2f3b12a29f7b1a2588f/README.md), [guest agent plist](https://github.com/cirruslabs/macos-image-templates/blob/d6a3774b296fb80aa42c2a4885d6eb364a909ffd/data/tart-guest-agent.plist), [guest daemon plist](https://github.com/cirruslabs/macos-image-templates/blob/d6a3774b296fb80aa42c2a4885d6eb364a909ffd/data/tart-guest-daemon.plist).

The current guest-agent RPC source ties attached exec commands to stream cancellation and has detached RPC support, but **Tart 2.41.1's CLI does not expose a detach option**. Do not use an attached exec/SSH exit as the sole runner lifecycle authority. Bootstrap an independent fixed guest service, then poll a small guest-owned status record using short exec calls. Keep credential payloads on stdin rather than argv: the guest agent logs executable/argument information. Pin the guest-agent version as part of the image; do not infer current-main features in an older published image. [Guest exec lifecycle](https://github.com/openai/tart-guest-agent/blob/6d4bd9c74ebbbc83d10ac2f3b12a29f7b1a2588f/internal/rpc/exec.go), [pinned CLI](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Exec.swift).

**Controller design inference:** journal job ID, generated VM name, image digest, guest bootstrap nonce/version, registration identity, phase, and hard deadlines before each external side effect. Guest status should distinguish bootstrap started, runner listening, job running, runner exited, and terminal reason; atomically persist it inside the disposable guest. After controller restart, reconcile journal + `list/get` + a short authenticated-to-the-VM status query. A surviving `tart run` can be observed through Tart's lock/control socket; no CLI API reattaches a new parent as its process owner. launchd may also terminate descendants depending on service lifecycle, so surviving-child behavior must be tested. Do not carry the exclusive slot descriptor into a child in a way that prevents the replacement controller from reconciling it.

Never infer successful GitHub job completion merely from VM shutdown, runner disappearance, a lost RPC, or the guest wrapper exiting. A terminal guest record is evidence for cleanup, while the GitHub job result is authoritative for workflow outcome. On ambiguous state, stop/delete the exact owned guest and retire its runner registration; do not re-execute the same payload automatically. Do not start another job until cleanup is confirmed. Host reboot destroys active VM execution; reconcile any stopped disk before new admission. Orphan names absent from the journal should block admission pending bounded ownership reconciliation, not trigger broad VM deletion. [Tart state/locking mechanics](https://github.com/openai/tart/blob/2.41.1/Sources/tart/VMDirectory.swift).

## Non-admin boot service and networking

LaunchDaemons run in the system context independently of a user GUI session; LaunchAgents have different session behavior. Configure an actual system LaunchDaemon with `_runner` identity, explicit absolute executable paths, working directory, HOME/PATH/TART_HOME, persistent private state/log directories, restrictive permissions, and backoff. Tart defaults to the current account's `~/.tart`, so a conventional service account with `/var/empty` home is insufficient without a writable dedicated home/TART_HOME and a usable account keychain. Keep host job credentials and production service files inaccessible to `_runner`; keep deployed code, executable parents, and privileged helper artifacts unwritable by `_runner`. This is a configuration proposal requiring on-host proof, not evidence that macOS27 service virtualization is supported in all contexts. [Apple daemon guidance](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/DesigningDaemons.html), [Tart home configuration](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Config.swift).

Keep the signed `tart.app` and embedded provisioning profile: the quick start explicitly requires executing its bundled binary to obtain needed entitlements. Do not rebuild/ad-hoc-sign or extract only its executable as an incidental Nix packaging change. `_runner` need not be an administrator merely to invoke that correctly packaged tool, but Softnet introduces a privileged setup boundary. [Official packaging warning](https://tart.run/quick-start/).

The keychain workaround must be designed explicitly and tested after a cold reboot. The official FAQ demonstrates an empty-password keychain; this note does not recommend silently weakening an existing user's keychain or persisting a password in Nix/argv. A dedicated service keychain, its unlock mechanism, and credential storage need a separate reviewed choice. Distinguish “macOS has booted with no GUI session” from disk preboot unlock and laptop sleep/power availability.

Apple TN3179 says macOS automatically allows local networking for **any launchd daemon**, root programs, and command-line tools run from Terminal/SSH including descendants; that exception does not apply to LaunchAgents. Therefore do not apply Tart FAQ's broad system-wide RFC1918 privacy exclusions by default. Test the real system-daemon process chain first, especially with Nix wrappers/signatures. [Apple local-network privacy](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).

Default Tart networking is shared NAT, not a LAN/host firewall; its FAQ documents reaching host services through the gateway. Softnet adds filtering and anti-spoofing, but its default policy permits public IPv4, the vmnet gateway, and incoming traffic. Use explicit `@host`, `@peers`, RFC1918, CGNAT/tailnet, link-local and other required deny rules; do not replace the repository's stronger policy with `--net-softnet` alone. CLI IPv4 rules are not proof of DNS/IPv6 isolation or public-address hairpin resistance. No host directories, clipboard, USB, audio, exposed ports, bridged networking, nested virtualization, or job-supplied flags are needed. [Softnet 0.25.0 model](https://github.com/openai/softnet/blob/0.25.0/README.md), [rule grammar](https://github.com/openai/softnet/blob/0.25.0/lib/proxy/rule.pest), [Tart flags](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Run.swift).

Softnet 0.25.0 requires macOS26+ and a matching SDK to build. It initially needs root through a root-owned setuid executable or narrowly configured passwordless sudo, then drops privileges after network setup. It is not a fully unprivileged runtime dependency. Tart's interactive convenience code can offer to chown/chmod Softnet; a no-login daemon cannot depend on that prompt. Provision a reviewed immutable/versioned helper path and exact privilege policy through Nix-managed host configuration, verify ownership/hash on startup and upgrade, and prove privilege dropping. A mutable user-owned helper or general sudo grant would defeat `_runner` separation. [Softnet installation requirements](https://github.com/openai/softnet/blob/0.25.0/README.md), [privilege escalation/drop implementation](https://github.com/openai/softnet/blob/0.25.0/src/main.rs), [Tart helper handling](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Network/Softnet.swift).

## Image provenance, defaults and licenses

Cirrus `macos-*-base`, `macos-*-xcode:N` and `macos-runner:*` are third-party images built from public Packer templates, **not GitHub-hosted runner images distributed by GitHub**. Base includes Homebrew and the GitHub Actions runner; Xcode adds toolchains, Flutter and other packages; runner variants carry multiple Xcodes. The installer currently selects the latest upstream `actions/runner` ARM64 release during image construction, so a template commit alone does not pin the resulting runner archive. Treat the OCI digest, build provenance, software manifest, runner version and checksum as review inputs. A digest guarantees selected content identity, not publisher trust or absence of credentials. [Variants](https://github.com/cirruslabs/macos-image-templates/blob/d6a3774b296fb80aa42c2a4885d6eb364a909ffd/README.md), [runner installer](https://github.com/cirruslabs/macos-image-templates/blob/d6a3774b296fb80aa42c2a4885d6eb364a909ffd/scripts/install-actions-runner.sh).

These images intentionally relax guest protections for CI. The reviewed vanilla templates use `admin` credentials, passwordless sudo and GUI convenience settings; base build workflows explicitly run SIP-disabling templates. Golden Gate vanilla checks FileVault off, configures Screen Sharing, and disables Gatekeeper using the provisioning UI path. Do not assume a hardened macOS guest or all versions having identical tweaks. A disposable validation boot must inspect SSH/screen-sharing state, guest auto-login, sudo, SIP, FileVault, installed agents, runner configuration, keychains, authorized keys, registry/Apple/Git credentials and retained provisioning artifacts. Build a derived reviewed image without host secrets or pre-registration, then re-check every promoted digest. [Golden Gate template](https://github.com/cirruslabs/macos-image-templates/blob/d6a3774b296fb80aa42c2a4885d6eb364a909ffd/templates/vanilla-golden-gate.pkr.hcl), [base workflow](https://github.com/cirruslabs/macos-image-templates/blob/d6a3774b296fb80aa42c2a4885d6eb364a909ffd/.github/workflows/base.yml), [base provisioning](https://github.com/cirruslabs/macos-image-templates/blob/d6a3774b296fb80aa42c2a4885d6eb364a909ffd/templates/base.pkr.hcl).

**License correction:** the official Tart 2.41.1 and Softnet 0.25.0 LICENSE files are **FSL-1.1-ALv2**, explicitly permitting internal use, excluding defined competing commercial uses, with Apache-2.0 conversion after two years for each software version. Neither inspected release license has an employee-count or CPU-core allowance. Do not state “free for organizations under 200 employees.” The live tart.run licensing page still describes older Fair Source 100-core/free tiers and $12,000/$36,000 paid tiers; that webpage conflicts with the selected release licenses and must not be applied as the current package terms. Recheck the exact bundled license for every version; any paid support/pricing claim needs current vendor confirmation. [Tart release license](https://github.com/openai/tart/blob/2.41.1/LICENSE), [Softnet release license](https://github.com/openai/softnet/blob/0.25.0/LICENSE), [conflicting legacy pricing page](https://tart.run/licensing/).

The image-template repository's MIT license covers its template code, not Apple macOS/Xcode licensing. Apple's Tahoe SLA §2B(iii) describes up to two additional virtual instances on an owned/controlled Apple-branded computer already running the Apple software for specified purposes including software development/testing. One guest is technically within that numeric ceiling, but the exact host/guest macOS agreement and acquisition method still matter. Check the selected macOS27 license and Xcode/SDK agreement before image redistribution or external service use; an accepted license inside an image does not remove the user's obligations. [Template license](https://github.com/cirruslabs/macos-image-templates/blob/d6a3774b296fb80aa42c2a4885d6eb364a909ffd/LICENSE), [Apple Tahoe SLA](https://www.apple.com/legal/sla/docs/macOSTahoe.pdf), [Xcode/SDK agreement](https://www.apple.com/legal/sla/docs/xcode.pdf), [Apple current SLAs](https://www.apple.com/legal/sla/).

## Proof gates before enablement

1. **Unprivileged local tests:** Rust fake Tart/guest/GitHub adapters exercise exact argv (no shell interpolation), JSON parsing, collision/partial-clone failures, journal writes before effects, concurrent admission, cancellation, expired credentials, bounded logs, deadlines, disk-floor handling, shutdown races, and restarts at every phase. Simulate a surviving Tart process without inherited slot deadlock. Unknown inventory and cleanup failures must prevent a second guest. These tests require no host virtualization or credentials.
2. **Disposable guest contract:** on an explicitly authorized VM host, inspect one pinned image's actual manifest/defaults; bootstrap a fixed guest service through agent and separately evaluate SSH only if needed; prove identity, input secrecy, status polling, runner single-job exit, log retrieval, timeout and runner-registration retirement. Kill the transport and controller independently; verify no job starts twice and evidence survives until cleanup.
3. **Exact host boot gate:** install through reviewed Nix/Comin configuration with the runner disabled by default; verify bundle signatures, helper hashes/ownership, `_runner` home/keychain, no admin membership, and secret/file separation. Cold reboot, leave GUI logged out, and prove Tart clone/run/exec/stop/delete as the actual LaunchDaemon. Repeat with locked screen and after tool/config updates. Do not substitute an interactive SSH success for this gate.
4. **Network gate:** from the guest test gateway/host on every active address, peer guests, LAN/router/NAS/printer/HA, tailnet/CGNAT, IPv6/link-local, DNS paths and public-address routes back into the LAN. Verify required GitHub/registry/artifact endpoints still work. Tie results to tool hashes, image digest, host OS and network configuration; revoke admission when these change. A caller-supplied `isolation_verified=true` is insufficient.
5. **Failure/storage gate:** measure base pull/cache size, clone allocation, idle/startup time, representative Xcode build peak RAM/storage, deletion reclaim, candidate image upgrade peak and bounded logs. Test guest disk full, host reserve reached, Softnet exit, stalled boot, force stop, daemon crash/restart and host reboot with an active guest. Prove cleanup reclaims the slot and leaves the host healthy before choosing final disk budgets or enabling real jobs.

All five gates remain open. This note does not authorize executing them or accessing the target host.

# GitHub contract for a small Tart runner controller

Research date: 2026-11-07. Documentation/source research only; no authenticated requests, credentials, hosts, or account changes. The primary agent independently verified `0x63616c/world-wide-webb` is public and `0x63616c/folding` is private; this note did not inspect their settings or workflows.

## Recommendation and scope

Use REST reconciliation for the initial Rust implementation: one controller, a fixed repository allowlist, one global active VM/runner slot, a fresh Tart clone and fresh repository-scoped JIT runner for each job. This is a design recommendation, not a GitHub-provided queue reservation protocol. Keep GitHub demand discovery behind an interface so scale-set demand can replace it later. Multiple Macs should initially remain workers of the same central controller/lease store; independent pollers cannot enforce a global one-job limit.

## Verified API behavior

- Discover runs with `GET /repos/{owner}/{repo}/actions/runs`, paginate at 100/page. Query **both `queued` and `in_progress`**, and preferably all other nonterminal states (`requested`, `waiting`, `pending`) rather than interpreting a run status as job demand. Status-filtered searches are capped at 1,000 results: detect saturation and split searches by creation windows, or fail visibly; never silently truncate. Old runs can be re-run, so a recent-created-only cutoff is insufficient. Run reads require repository **Actions: read**. Cancel/force-cancel are separate write operations; omit them from the controller's permission/scope. [Workflow runs REST](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-repository)
- For each active run, paginate `GET /repos/{owner}/{repo}/actions/runs/{run_id}/jobs?filter=latest&per_page=100`; alternatively use `/attempts/{attempt_number}/jobs` for an explicitly selected current attempt. `latest` excludes old executions; `all` includes them. Job reads require **Actions: read**. Job records expose `id`, `run_id`, `status`, `labels`, `runner_id`, `runner_name` and group fields. Select actual `status == queued` records; use job IDs, not display names, as identities. Retain run attempt in local correlation/state. `GET /actions/jobs/{job_id}` revalidates a candidate immediately before provisioning. [Workflow jobs REST](https://docs.github.com/en/rest/actions/workflow-jobs)
- A matrix expands one definition into multiple jobs; `max-parallel` and fail-fast affect execution. `needs` blocks downstream jobs until prerequisites resolve, with conditional exceptions. Therefore do not parse YAML to predict demand or mark a run permanently handled after its first job. A run may contain a hosted job in progress and a homelab job waiting, or gain a downstream queued job later. Exact REST visibility/status timing for blocked matrix/dependency jobs is not documented here and needs a fixture test. [Matrix jobs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/run-job-variations), [Job dependencies](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-jobs)
- Matching is cumulative: a runner must satisfy **every** requested label, plus any group constraint. Default labels describe self-hosted/OS/architecture, but they can be omitted during conventional registration. Labels are case-insensitive. Proposed accepted profile is `[self-hosted, macOS, ARM64, homelab-tart]`; compare normalized requested-label sets against explicitly supported image profiles and require the dedicated label. Never copy arbitrary requested labels onto an image: labels do not validate hardware. Reject unsupported group-based routing in v1. [Workflow runner matching](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/use-in-a-workflow), [Label semantics](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/apply-labels)

## Registration, identity and permissions

A GitHub App can be installed on a **personal account**, restricted to selected repositories. Choose only the allowlisted repositories; do not require an organization migration. [Install your own app](https://docs.github.com/en/apps/using-github-apps/installing-your-own-github-app)

For this REST-only design the minimum explicit repository permissions are **Actions: read** (runs/jobs/logs) and **Administration: write** (JIT creation and runner deletion; includes runner reads). Metadata read is implicit in GitHub Apps. No Contents, Workflows, Checks, or organization Self-hosted runners permission is needed for these operations. `POST /repos/{owner}/{repo}/actions/runners/generate-jitconfig` requires `name`, `runner_group_id`, and 1–100 `labels`; optional `work_folder` defaults to `_work`. It returns `runner` and `encoded_jit_config`. Repository scope is selected by the URL. The documented example uses group ID `1`; the contract only defines this as a runner-group ID, **not a universal constant**. There is no job-ID parameter. The separate registration token expires after one hour; do not assume that documents the JIT blob's lifetime. [Runner REST](https://docs.github.com/en/rest/actions/self-hosted-runners#create-configuration-for-a-just-in-time-runner-for-a-repository)

**Gate:** verify personal-repository JIT creation with the selected app and proposed `runner_group_id: 1` before shipping. The public repository JIT schema does not explain how personal repositories resolve that required ID, nor offer a repository runner-group discovery endpoint. Conventional runner source selects a returned internal default pool, rather than hardcoding `1`; this is evidence against treating the example as a guaranteed identifier. If the JIT call fails, stop and resolve the contract; do not silently switch scope or broaden permissions. [Runner configuration source](https://github.com/actions/runner/blob/main/src/Runner.Listener/Configuration/ConfigurationManager.cs)

Installation access tokens expire after one hour and can be further restricted by repository IDs and permissions when minted. Keep the App private key/JWT and installation token on the trusted controller; mint/cache/refresh there, scope runner creation to the selected repository. [Installation authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation)

## Assignment, lifecycle and failure handling

GitHub chooses an online idle runner matching labels/groups; an assignment not picked up within 60 seconds is requeued. A job without a suitable runner can remain queued up to 24 hours. JIT runners process at most one job. Consequently the selected candidate is a **capacity hint**, not a claim: another eligible job in that repository can land on the runner. Observe the actual `runner_id` association; never destroy a busy VM merely because the original candidate was cancelled. [Routing contract](https://docs.github.com/en/actions/reference/runners/self-hosted-runners#routing-precedence-for-self-hosted-runners), [JIT security contract](https://docs.github.com/en/actions/reference/security/secure-use#using-just-in-time-runners)

JIT runners that never execute are eventually removed automatically, but the removal documentation does not specify the interval. No explicit TTL/`expires_at` for `encoded_jit_config` was found in the public REST contract. Generate it only after the VM is ready, never pre-mint an entire matrix backlog; treat it as a one-runner secret, never replay a failed blob. Validate delayed-start expiry and replay rejection separately; do not promise a 60-minute job runtime limit. [Removal behavior](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/remove-runners)

Design requirements: reserve the local slot durably before clone/JIT creation; use unique runner/VM names; record returned runner ID; reconcile managed resources on restart. Re-fetch queue state before creating; a cancellation race after that is normal. Bound boot and **idle-unassigned** time separately from running time. Allow the official runner to receive cancellation; reap only after exit or an explicit timeout policy with runner/job evidence. On API errors/backoff retain the active lease and do not infer completion from missing/stale demand. Clean up only owned runners and VMs. Terminal/404 candidates are dropped; stale queues trigger bounded retries/alerts, not workflow cancellation.

By default runners self-update. With automatic updates disabled, update within 30 days of each release; critical security releases can block work immediately. Prefer fresh baked images plus automatic updates initially; JIT REST does not expose a disable-update request field. Verify the generated runner's behavior before selecting an immutable-image policy. [Runner updates](https://docs.github.com/en/actions/reference/runners/self-hosted-runners#runner-software-updates-on-self-hosted-runners)

Export `_diag/Runner_*`, `_diag/Worker_*` and controller/VM lifecycle events before deleting the clone; GitHub job logs do not replace runner diagnostics. Attach repo/run/attempt/job/runner/VM identifiers, with retention and redaction. [Diagnostics](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/monitor-and-troubleshoot)

JIT config is encoded credential material, not harmless configuration: official runner code decodes it into configuration/credential files. Inject into the guest without controller tokens, secret-bearing logs or shell history; never bake it into the reusable image. Guest compromise must not expose controller credentials, host mounts, host SSH agents, or the control network. Repository allowlisting alone does not authorize untrusted PR execution; choose trusted-event/approval policy before enabling workflows. Clean disposable environments and minimum network/secret access remain necessary. [JIT loading source](https://github.com/actions/runner/blob/main/src/Runner.Listener/Runner.cs), [Security guidance](https://docs.github.com/en/actions/reference/security/secure-use)

## Delivering JIT without argv or environment secrets

**Decision after research:** the implementation plan chooses the supported guest-only `ACTIONS_RUNNER_INPUT_JITCONFIG` path, supplied by a fixed helper reading stdin. The internal decoder below is a researched alternative, **not** the selected implementation. Avoiding a short-lived credential environment in the already credential-bearing disposable guest does not justify maintaining GitHub's internal file format here. The host App credentials never enter that environment. See [the final plan](../runner-controller-plan.md#trust-and-secrets).

Source check: the public latest-release endpoint returned **v2.338.2** during this research; a deployment must pin the chosen archive/version/checksum and revalidate these internals for that exact version. `CommandSettings.GetJitConfig()` calls `GetArg("jitconfig")`, which checks argv and then `ACTIONS_RUNNER_INPUT_JITCONFIG`. It does not prompt or read stdin. No `ReadJitConfig`, file-path flag, or `--jitconfig -` stdin convention exists in the inspected pinned `CommandSettings`/`Runner` path. The environment alternative is removed after parsing, but still violates the no-environment-secret requirement. [Pinned CommandSettings](https://github.com/actions/runner/blob/v2.338.2/src/Runner.Listener/CommandSettings.cs#L222)

**Proposed implementation choice, with an explicit compatibility gate:** send the encoded blob from controller memory through `tart exec -i <vm> <fixed-helper>` stdin. The guest helper reads a bounded payload, decodes Base64 → JSON string-to-string map → Base64 file values, materializes the files in the clean runner root, then starts `./run.sh` with **no JIT argument or secret environment variable**. This reproduces the macOS portion of the pinned official loader, which otherwise does exactly those writes before loading settings. Preserve the JIT-provided ephemeral/identity/credential settings; do not invoke `config.sh`, re-register, modify fields, or reconstruct credentials. This is an internal format adapter, not a documented GitHub stdin/file API. [Pinned JIT loader](https://github.com/actions/runner/blob/v2.338.2/src/Runner.Listener/Runner.cs#L234)

The pinned configuration store recognizes a configured runner from its settings file; standard paths include `.runner`, `.credentials`, and `.credentials_rsaparams`. The normal shell helper invokes `Runner.Listener run` and handles update/restart exits. Preloading therefore allows the unmodified official runner to follow its usual configured-runner startup path; the server-side JIT identity still supplies the one-job semantics. Exact field/file-map shape and successful execution must be validated against a real newly generated JIT config before shipping. [Pinned configuration store](https://github.com/actions/runner/blob/v2.338.2/src/Runner.Common/ConfigurationStore.cs#L236), [Pinned path definitions](https://github.com/actions/runner/blob/v2.338.2/src/Runner.Common/HostContext.cs#L445), [Pinned run helper](https://github.com/actions/runner/blob/v2.338.2/src/Misc/layoutroot/run-helper.sh.template)

Helper acceptance requirements: no echo/tracing or raw parser error payloads; size limits; expected map-key allowlist tied to the pinned runner; reject absolute paths, traversal, symlinks and preexisting credential files; private directory and exclusive 0600 files under umask 077; verify required settings/ephemeral identity; close input and remove the raw blob buffer before launching; no host secret files or shell interpolation. Keep controller App credentials entirely outside the guest. The decoded guest credential files intentionally remain for the runner's lifetime and disappear with the disposable VM. Log-export filtering must exclude them. Test normal one-job exit, update/restart, rejected malformed maps, cancellation and crash recovery. If maintaining this version-sensitive adapter is unacceptable, the strict no-argv/no-environment constraint blocks the documented `--jitconfig` path; do not disguise argv expansion as stdin delivery.

## Enforcing trusted code on the personal public repository

**Concrete v1 recommendation: keep `world-wide-webb` disabled in controller configuration and do not register a runner there until a server-side trust gate is proven.** Start with the private repository only after confirming its collaborators/fork policy meet the same trust model. Polling only trusted branches does not constrain which eligible job GitHub can assign once a runner is registered. Protected branches and an `if` in the intended workflow likewise do not constitute repository-runner authorization against a different PR workflow.

Current GitHub supports a stronger personal-repository setting: **Settings → Features → Pull requests → Collaborators only**, or disable pull requests entirely. Personal-repository collaborators are invited users. If accepting outside PRs is unnecessary, recommend collaborator-only PRs plus audit/drain of every existing untrusted queued/rerunnable run before enabling the runner. This closes new outside PR creation, but existing runs and other trigger paths remain an acceptance gate. [Disable/restrict pull requests](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/disabling-pull-requests)

If outside PRs must stay open, **Require approval for all external contributors** is the appropriate server-side approval setting, not first-time-only approval. However approval explicitly permits that code to execute, and GitHub says runner security guidance still applies regardless of approvals. The user's strict trusted-branches-only requirement therefore needs an additional proven execution boundary; merely promising never to approve suspicious jobs is insufficient. A conservative option is a separate private execution repository: a trusted dispatcher submits only reviewed immutable SHAs, and the runner is registered only there. This adds dispatch/checkout design and permissions; it is not included in the minimal v1 App permission set. [Repository Actions approval policy](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)

Audit all event paths before enabling public-repo execution: `pull_request_target` runs in the base context and must not check out/run untrusted head code; `workflow_run`, issue-comment and dispatch workflows can also bridge untrusted inputs into privileged execution. Protected main alone cannot establish provenance of code/artifacts fetched by these workflows. [Event security semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request_target)

A baked `ACTIONS_RUNNER_HOOK_JOB_STARTED` is a possible defense in depth: documented hooks run synchronously after assignment and before the job, can inspect default variables/event payload, and nonzero exit prevents the job from running. Hooks have no built-in timeout and execute as the runner account. Do **not** call a simple environment-variable check a proven security boundary: validate actual run/attempt/ref/SHA against controller authorization, including job-level environment overrides and reruns, and prove malicious fixtures cannot bypass/replace the hook before adopting this alternative. Keep public execution gated in the meantime. [Pre-job hook contract](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/run-scripts)

## Alternatives and acceptance gates

The official standalone **actions/scaleset** client is Go, currently labeled public preview; no official Rust SDK is offered in that repository. It supports repository/organization/enterprise scope and arbitrary VM provisioning without Kubernetes. Its protocol creates a scale set, maintains message sessions, long-polls (~50-second server hold), acknowledges messages, reports maximum capacity, and scales using current `TotalAssignedJobs` statistics (includes running jobs), rather than counting events. It also refreshes credentials. Rust would need a Go helper or port of those behaviors. It solves demand delivery better but adds a protocol/controller layer beyond this small initial REST poller. ARC is the Kubernetes reference implementation. Webhooks are another official demand signal, with delivery/reconciliation overhead. [Scale-set client](https://github.com/actions/scaleset/blob/main/README.md), [Autoscaling options](https://docs.github.com/en/actions/reference/runners/self-hosted-runners#autoscaling)

GitHub recommends webhooks over REST polling. For the deliberate low-volume polling exception, use a modest fixed interval, authenticated conditional requests/ETags, all pagination, `x-poll-interval`, `Retry-After`/rate-reset and bounded exponential backoff. Measure requests/latency before adding repositories. [REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)

Before implementation approval, define executable acceptance fixtures for: personal-repo JIT/group ID and exact app permissions; ARM64/macOS JIT labels; hosted+queued mixed run; dependency chain; matrix with max-parallel/fail-fast; full and failed-job reruns of old runs; cancellation before boot and after assignment to a different job; expired/consumed JIT; controller restart at every create/delete boundary; API outage/rate-limit/partial pagination; runner update required; logs collected and secrets absent. Tests involving authenticated GitHub mutations are future gates, not performed by this research.

# Blockr

Universal SwiftUI product: iPhone/iPad app, native Mac companion and menu-bar extra. APP-14; visual reference is APP-13 pass 2. No design source is copied into this change.

## Build and test

```sh
swift test --package-path apps/blockr --jobs 4
(cd apps/blockr && xcodegen generate)
xcodebuild -project apps/blockr/Blockr.xcodeproj -scheme Blockr -sdk iphonesimulator -jobs 4 CODE_SIGNING_ALLOWED=NO build
xcodebuild -project apps/blockr/Blockr.xcodeproj -scheme BlockrMac -destination 'generic/platform=macOS' -jobs 4 CODE_SIGNING_ALLOWED=NO build
```

Requires Xcode 27 or later. CI runs on GitHub-hosted `xcode-27` with Xcode 27.1 at `/Applications/Xcode_27.1.app/Contents/Developer` and builds both platforms, runs the package tests and publishes the generated project as `blockr-generated-project`. The checked-in project is obtained from that artifact on Linux. `BlockrUITests/ScreenshotTests` uses `--screenshots` synthetic fixtures, without requesting authorization or writing shared state; capture via the shared PR screenshots workflow. No fixture code runs without that launch argument.

## iOS protection

Individual Screen Time authorization, local FamilyActivityPicker, Blockr's named ManagedSettings store, and four extensions. App/category/domain tokens are Codable device-local data only. Typed hostnames use `webContent.blockedByFilter`; tokens use system shields. Typed-host filtering uses the system web-content policy, so not every browser/transport is guaranteed. Blockr never resolves opaque app identities. Blockr requests the token for its own known bundle identifier and, when available, excludes it from direct app shields and category policies. This does not inspect or resolve other selected identities. The system's optional token and own-app exemption need signed-device verification; avoid selecting Blockr itself.

The authorized iOS group editor embeds a “Most used” DeviceActivityReport beside the app picker controls. The `DeviceActivityReport` ExtensionKit extension aggregates the last seven days of iPhone/iPad app usage and displays up to eight app labels, relative duration bars and short durations. Report data and tokens stay in the report sandbox; it cannot add apps to the selection or send usage back to Blockr. Use the picker to select the apps shown. Empty reports show “No activity.” Signed-device verification is required for report loading, system app labels and usage; the simulator screenshot fixture cannot supply protected Screen Time history. XcodeGen embeds this target under `Extensions/`, while the other Screen Time extensions use `PlugIns/`.

An immutable local selection snapshot and lock intent are persisted before scheduling. The monitor is registered before restrictions apply. All mutations recheck active locks in shared storage. No early unlock, pause, cancellation or lock extension. The monitor recomputes the union of all remaining sessions and restores Blockr's previous app-removal restriction only when none remain. Launch reconciles expired sessions without assuming continuity. A failed local application remains visibly unprotected and can be repaired with local picks. Overlapping remote sessions retain independent original expiry times. Less than 15 minutes remaining cannot be installed as a new Screen Time interval and is reported as unprotected, never silently extended.

Shared JSON uses NSFileCoordinator and atomic replacement across processes; reads fall back to the atomic file if coordination fails. Decode failures never reset the file to an unlocked state. Shield display first reads a compact, device-local App Group defaults snapshot written whenever enforcement installs or clears shields, avoiding the full history and file coordination. It shows a lock icon, remaining duration, “until <time> · <group>” and Close. Matching app/category/domain metadata wins; an unknown token falls back to the latest installed live expiry. With no live metadata it shows only Locked and Close. Shield diagnostics log reasons without names or tokens; monitor processes cannot display storage errors and the app surfaces them on next launch. DeviceActivity callbacks may be late. Revoking access, uninstalling the app, OS scheduling and clock changes can interrupt protection. Blockr makes no tamper-proof guarantee.

Stats count shield **button taps**, not every blocked-open attempt. Successful local monitor completions with no observed interruption count toward unbroken locks. Expired sessions recovered only on app launch are conservatively interrupted. Time locked deduplicates overlaps. Estimated time saved and per-app usage show unavailable: no fabricated baseline or export of protected report data. A privacy-preserving DeviceActivityReport baseline needs a separate signed-device feasibility check.

## iCloud switch and deployment

The default Release and Debug entitlements **do not contain iCloud or push entitlements**. `BLOCKR_CLOUD_ENABLED=NO` prevents even constructing CKContainer: invoking it without entitlements can terminate an app. UI shows “iCloud unavailable.” Local locks work independently. The iCloud container is not assumed to exist.

Before enabling, confirm/create `iCloud.com.calumwebb.blockr` in the Apple developer account, attach it to **both** platform app identifiers for `com.calumwebb.blockr`, enable CloudKit, and regenerate their profiles. Add app-only entitlements `com.apple.developer.icloud-container-identifiers = [iCloud.com.calumwebb.blockr]`, `com.apple.developer.icloud-services = [CloudKit]`, and the appropriate `aps-environment` / `com.apple.developer.aps-environment` push entitlement for each platform. Set `BLOCKR_CLOUD_ENABLED=YES` only for configurations with those entitlements. Do not add iCloud to the Screen Time extensions. Deploy the `BlockrReplica` record type with a `payload` Bytes field to the production schema before TestFlight. Verify account status, custom zone and silent pushes with two signed devices. CI's default signing does not opt in until this is confirmed.

Sync uses a custom private zone with one versioned Codable metadata replica record. Persistent local state is the outbound queue. Each round fetches the latest change tag, deterministically merges logical revisions/tombstones and immutable lock unions, then conditionally saves; server-record conflicts refetch and merge up to four times. Failed sends preserve local intent for retry. Paginated record queries and indexes are unnecessary for this single-record schema. A 900 KB guard preserves local data and reports an error before CloudKit's record-size limit; an eventual large-history migration should split immutable sessions into records. Sync runs on foreground entry, every 30 seconds while the app process is running (including the Mac menu bar) and best-effort iOS zone-subscription silent pushes. Offline/force-quit devices cannot be promised immediate enforcement. Up to date describes a completed local exchange, not acknowledgement by every device.

Only group UUID/name, normalized typed hosts, user-entered category hint, custom durations/tombstones and immutable lock schedules cross devices. Picks, tokens, attempts and enforcement receipts do not. Group edits/deletions cannot alter a lock snapshot. An account change detaches previous metadata and picks; already active local locks continue to expiry and are excluded from the new account's outbound payload. Local reset is blocked during any lock, removes only the local replica and does not remotely delete records.

## Native macOS limits

Native macOS has no public FamilyActivityPicker, AuthorizationCenter, ManagedSettingsStore or DeviceActivityCenter support. Catalyst availability does not establish native Mac support. Mac is a group/schedule/stats companion and explicitly shows “Not protected here” for remote sessions. Local Mac starts require an enabled, healthy signed filter and at least one typed website. It never starts a pretend protected timer. Desktop app blocking, app-removal prevention and Screen Time usage are unavailable. Manual macOS Screen Time website rules are separate and cannot be installed or expired by Blockr.

**The timed Mac website filter is implemented but gated off in unsigned/unprovisioned builds** (`BLOCKR_FILTER_ENABLED=NO`). `ContentFilter` is an embedded `NEFilterDataProvider` system extension with a setup controller using `OSSystemExtensionRequest` and `NEFilterManager`. It reads shared policy without writing or exporting traffic; independently checks absolute expiry on every verdict; matches exact typed hosts and their subdomains; and continues observing existing flows so new locks can affect already-open connections. The policy refreshes once per second. It never invents an HTTPS block page. A health-only app-group XPC interface returns policy IDs; enabling a configuration alone does not mark a lock protected. It retains original expiry when policy reads fail and reports unhealthy. Mac app picks are always unavailable and a group with iPhone selection intent shows partial coverage even when its websites are protected.

A usable signed release needs the Blockr-only `com.calumwebb.blockr.ContentFilter` identifier, registered App Group association, Network Extension distribution entitlements, system-extension install entitlement on the Mac app, and Mac App Store profiles. `register_ids` supports these two Mac identifiers only via `macos_registration_targets`; it never generates a Mac certificate. Confirm the App Group relationship and Mach service sandbox access before setting `BLOCKR_FILTER_ENABLED=YES` in a signed Mac build installed under `/Applications`. The default companion explicitly reports the unavailable filter. An unsigned filter or merely opening Settings is not proof of protection. No hosts-file changes, TLS interception, private APIs or fabricated “enabled” state are used. This requires signed-device testing across Safari/Chromium/Firefox, existing connections, QUIC/DoH, private browsing, VPN coexistence, expiry with Blockr quit and provider restart before claiming coverage. Provider traffic callbacks inspect only host metadata and never log content. See Apple's [content filter sample](https://developer.apple.com/documentation/networkextension/filtering-network-traffic) and [deployment technote](https://developer.apple.com/documentation/technotes/tn3134-network-extension-provider-deployment).

Mac TestFlight is not configured. The shared lane uploads iOS only; Mac distribution needs verified Mac App Store application profiles/certificate compatibility and a Mac Installer Distribution certificate for packaging. No certificate was created, revoked or reconfigured.

## Release

Five iOS Blockr bundle IDs with family-controls; all but DeviceActivityReport also use the app group. `register_ids app:blockr` enables FAMILY_CONTROLS using the ASC API without touching other apps. Blockr App Store profiles regenerate (`force: true`) on each CI release so approved entitlements are included. `scripts/verify-blockr-profile.sh` checks all five regenerated profiles carry Family Controls and the expected team/App ID before archive without printing profile contents. The new `com.calumwebb.blockr.DeviceActivityReport` App ID needs **Family Controls (Distribution)** enabled at developer.apple.com before App Store signing (it has no App Group entitlement: the report reads nothing shared); its profile is `Blockr DeviceActivityReport CI App Store`. API registration alone does not grant Distribution support. Archive entitlement diagnostics scan both `PlugIns/` and `Extensions/`. TestFlight uses app 6829523373, group Internal. CI waits for processing and group distribution; upload alone is insufficient evidence.

Required signed-device acceptance: authorization deny/retry/revoke, picker/category overlap, typed domains/subdomains, shield fallback and Close actions, app-removal restoration, monitor expiry with app killed/rebooted, concurrent remote locks, short remaining intervals and account switch/offline conflict recovery. Simulator and package tests cannot prove these system behaviors.

### Current distribution blocker (November 1)

The standard `FAMILY_CONTROLS` capability is present on the four pre-report iOS IDs, and the registration workflow succeeds. Nevertheless, forced regeneration of the app's App Store profile failed the entitlement check: `Print: Entry, "Entitlements:com.apple.developer.family-controls", Does Not Exist`. See [the signed CI attempt](https://github.com/0x63616c/apps/actions/runs/41350496157). No IPA was archived or uploaded. The three extension profiles have not yet reached verification because the app profile check stops the lane first.

The ASC client's managed-capability discovery endpoint was also tested: `The specified resource does not exist - The path provided does not match a defined resource type.` See [the API probe](https://github.com/0x63616c/apps/actions/runs/41351173198). That temporary probe was removed after confirming the unsupported endpoint; normal ID registration remains available. A standard capability's presence is not evidence of Distribution support. In Certificates, Identifiers & Profiles, enable the approved **Family Controls (Distribution)** managed capability for `com.calumwebb.blockr`, `com.calumwebb.blockr.ShieldConfiguration`, `com.calumwebb.blockr.ShieldAction`, `com.calumwebb.blockr.DeviceActivityMonitor` and the new `com.calumwebb.blockr.DeviceActivityReport` specifically, then rerun the branch TestFlight workflow. The lane will regenerate and verify every Blockr profile before archive. Do not remove the entitlement or bypass the verification gate. Apple's [distribution capability guidance](https://developer.apple.com/documentation/familycontrols/requesting-the-family-controls-entitlement) and [distribution restrictions guidance](https://developer.apple.com/forums/thread/721563) explain the distinction from team approval/development access.

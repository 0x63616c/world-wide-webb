# Beszel for two native Mac hosts

Researched 2026-11-08. Research only: no deployment, host access, credentials, or Cloudflare/account changes. Source baseline is upstream **v0.21.1**, released 2026-10-22, tag commit `e2ed147a5aa6472e6462521632ccc7101668132c`. Existing repository changes were preserved. [Release](https://github.com/henrygd/beszel/releases/tag/v0.21.1).

## Simplest recommendation

**Design inference informed by the primary agent's live topology inspection:** run the hub as another Compose service in the existing services Colima VM on `homelab-mac-mini`; run native agents on the Mini and MacBook as Nix-defined system LaunchDaemons with dedicated service identities and writable state directories. Reuse the existing Compose update/backup pipeline and Cloudflare Tunnel/Access configuration in `world-wide-webb` for `https://beszel.worldwidewebb.co`. This adds no VM. cloudflared runs with host networking inside the services VM, so a native macOS loopback listener would be in a different network namespace. Publish the hub on VM loopback for cloudflared. Use Beszel's own SSH transport exclusively over Tailscale initially: the hub dials each Mac agent's tailnet address on 45876. **The services VM's route to those tailnet addresses is unproven** and must be tested from the actual hub container before committing to this transport. This avoids a second HTTP origin, WebSocket registration secrets, and Cloudflare service-token exceptions. This SSH listener is Beszel's embedded metrics protocol, not macOS Remote Login. [Connection model](https://beszel.dev/guide/security), [agent installation](https://beszel.dev/guide/agent-installation).

For the first release, use an ordinary Beszel login behind the existing Cloudflare Access policy. An optional later simplification is to use the Access identity through `TRUSTED_AUTH_HEADER=Cf-Access-Authenticated-User-Email`, **only after confirming the actual proxy peer** and restricting `TRUSTED_PROXY_IPS` to that peer. An existing Beszel user with the matching email is required; this mode looks up users and does not provision them. Keep a separate recoverable PocketBase superuser credential. The unrestricted default trusts the header from any caller, so a remotely reachable origin without the proxy allowlist permits impersonation. Avoid `AUTO_LOGIN`. IP allowlisting validates the proxy connection peer, not the Access JWT itself; a loopback publication or broad Docker subnet allowlist must not be mistaken for a proven identity boundary. [Pinned auth middleware](https://github.com/henrygd/beszel/blob/v0.21.1/internal/hub/api.go).

## Packaging and native agents

The release actually contains `beszel_darwin_arm64.tar.gz` and `beszel-agent_darwin_arm64.tar.gz`; the release build enables Darwin ARM64 for both with `CGO_ENABLED=0`. A native hub is technically possible, but the existing services VM is the simpler fit for this deployment. Pin the hub container image to this version and a reviewed digest. The hub is a foreground `beszel serve --http ADDRESS:8090` process; upstream requires the operator to create persistent service management for manual binary installs. Homebrew agent installation is documented, but its user service does not establish pre-login system-daemon behavior. Native launchd management is an implementation inference, to be proven after a cold reboot. [Release assets/build matrix](https://github.com/henrygd/beszel/blob/v0.21.1/.goreleaser.yml), [binary installation](https://beszel.dev/guide/hub-installation), [Homebrew installer](https://github.com/henrygd/beszel/blob/v0.21.1/supplemental/scripts/install-agent-brew.sh).

Current nixpkgs unstable has Beszel 0.21.1, builds both binaries (`beszel-hub`, `beszel-agent`), and includes Darwin-specific handling; that does not prove the repository's pinned nixpkgs revision contains it or builds successfully. Prefer that package for native agents if the locked revision passes an aarch64-darwin build; otherwise package the upstream agent release archive with a fixed hash. Native hub packaging remains an alternative, not the recommended topology. Pin the same version for both roles; upgrades belong in Nix, not `beszel update` or an upstream automatic-update installer. Set `CHECK_UPDATES=false`. [nixpkgs package](https://github.com/NixOS/nixpkgs/blob/nixpkgs-unstable/pkgs/by-name/be/beszel/package.nix).

## Bootstrap, configuration and secrets

On a fresh data directory, `USER_EMAIL` plus `USER_PASSWORD` creates both the application user with admin role and a PocketBase superuser with that password. These are first-install migration inputs, not ongoing password reconciliation. The minimal automation is the existing secret pipeline rendering a mode-0600 runtime Compose `env_file` outside Git and `/nix/store`, containing `USER_EMAIL` and `USER_PASSWORD`; Compose passes them as environment rather than argv. Source inspection found no `USER_PASSWORD_FILE` support. Migration creates the users before the serving hook synchronizes `config.yml`, preventing a public first-user race. Repeated startup does not recreate the users. Remove the bootstrap inputs after initialization if desired, and retain recovery access securely. Never embed it in a Nix store derivation or plist. OAuth/OIDC is supported through PocketBase collection configuration with provider credentials and callback `/api/oauth2-redirect`; it adds configuration with no benefit if Access already supplies the required identity. `DISABLE_PASSWORD_AUTH` governs application password login and is not a substitute for protecting the PocketBase administration surface. [Bootstrap migration](https://github.com/henrygd/beszel/blob/v0.21.1/internal/migrations/initial-settings.go), [OIDC setup](https://beszel.dev/guide/oauth).

For **SSH-only agents**, set the hub's public `KEY`/`KEY_FILE` and `LISTEN` on each agent; omit `HUB_URL` and `TOKEN`. The hub generates and stores its private `id_ed25519` in its data directory; preserving this key avoids redistributing public keys after recovery. The hub does not write a public `.pub` file: derive the public key with `ssh-keygen -y` inside the protected host context or retrieve the authenticated `/api/beszel/info` result once, then commit only the public `KEY` to the Nix agent configuration. This is a one-time deployment dependency and does not require a registration API script. Agents do not need macOS login credentials or the host's SSH private keys. Restrict the remote listener to its Tailscale address and tailnet policy to the hub; verify restart/retry behavior if Tailscale is not ready when launchd starts. [Hub key generation](https://github.com/henrygd/beszel/blob/v0.21.1/internal/hub/hub.go), [agent variables](https://beszel.dev/guide/agent-installation).

If outgoing-only connections are later needed, use `HUB_URL` pointing at a private tailnet HTTP(S) origin, `KEY`, and a distinct per-system `TOKEN_FILE`; set `DISABLE_SSH=true` on both hub and agents. WebSocket registration uses `/api/beszel/agent-connect`. This is an alternative, not an additional initial transport; public Access authentication need not be bypassed for agent traffic. Prefer per-system tokens to a universal enrollment token. [Transport switches](https://beszel.dev/guide/environment-variables), [connection troubleshooting](https://beszel.dev/guide/common-issues).

Systems can be declared in `DATA_DIR/config.yml` with names, hosts, ports and user emails. **It is authoritative:** systems absent from a nonempty config are deleted on synchronization; an empty list skips synchronization. Identity is the concatenated name, host and port. Changing any of those creates a replacement and deletes the old system; its statistics have a cascading-deletion relation, so historical stats are deleted too. Use stable canonical names/endpoints and back up before inventory identity changes. Optional tokens also live here, so a token-bearing config must be generated outside the Nix store. For two fixed SSH systems, a token-free declarative inventory is sufficient. [Pinned config implementation](https://github.com/henrygd/beszel/blob/v0.21.1/internal/hub/config/config.go), [collection schema](https://github.com/henrygd/beszel/blob/v0.21.1/internal/migrations/0_collections_snapshot_0_20_0.go).

## Persistence, retention and recovery

Mount the hub's persistent Compose volume at `/beszel_data`, as documented upstream; a native alternative needs an explicit `--dir` path outside `/nix/store` because its default is relative `beszel_data`. Preserve the entire directory, including databases, settings, users and the hub private key. Agent `DATA_DIR` stores its fingerprint; give each service a persistent owned directory too. [Hub command](https://github.com/henrygd/beszel/blob/v0.21.1/internal/cmd/hub/hub.go), [agent state](https://github.com/henrygd/beszel/blob/v0.21.1/agent/data_dir.go).

Retention is built-in tiered history, not indefinite one-minute samples: 1-minute records for 1 hour, 10-minute for 12 hours, 20-minute for 24 hours, 2-hour for 7 days, 8-hour for 30 days. Deletion code implements these tiers; do not promise a configurable long-term metrics warehouse. [Pinned retention](https://github.com/henrygd/beszel/blob/v0.21.1/internal/records/records_deletion.go).

Upstream supports built-in backup/restore to local disk or S3-compatible storage, or stopping the hub and copying the whole data directory. Choose one off-host backup destination and test restore into an isolated directory before enabling routine backups. A raw live SQLite file copy is not the documented offline-copy procedure. Back up before package upgrades; binary rollback alone does not undo database migrations. [Official backup/restore guidance](https://beszel.dev/guide/hub-installation#backing-up-the-hub).

## Actual macOS coverage and limits

Host CPU/load, memory, filesystem usage/disk I/O and network counters come through native platform collectors; the source explicitly avoids substituting Docker Desktop's Linux VM CPU/memory totals for macOS host totals. macOS battery reporting uses `ioreg`; Wi-Fi RSSI uses CoreWLAN through `osascript`, with possible SSID redaction. Sensor visibility and APFS disk accounting must be checked on the actual hardware. Do not equate Beszel memory usage with Activity Monitor memory pressure, or promise accurate swap/compression/SSD wear/thermal throttling fields without checking their actual values. [System collection](https://github.com/henrygd/beszel/blob/v0.21.1/agent/system.go), [memory](https://github.com/henrygd/beszel/blob/v0.21.1/agent/memory.go), [disk](https://github.com/henrygd/beszel/blob/v0.21.1/agent/disk.go), [battery](https://github.com/henrygd/beszel/blob/v0.21.1/agent/battery/battery_darwin.go), [Wi-Fi](https://github.com/henrygd/beszel/blob/v0.21.1/agent/wifi/wifi_darwin.go).

Apple Silicon GPU monitoring is experimental and opt-in. `GPU_COLLECTOR=macmon` is recommended upstream and does not require root; `powermetrics` requires privilege. Start with ordinary host metrics and add pinned macmon only if GPU metrics are useful. Do not run the entire agent as root merely to obtain optional GPU graphs. [macOS GPU guidance](https://beszel.dev/guide/gpu#apple-silicon-macos).

No native Tart, per-VM-run, Xcode-job, or launchd-service attribution was found in the v0.21.1 agent/entity source. Host graphs can show aggregate load while a runner job executes, but cannot identify its resource use or completion by themselves. Beszel's container metrics concern Docker/Podman, and service monitoring concerns systemd. Per-run metrics remain a separate runner-controller concern; adding agents inside disposable guests would introduce enrollment, cleanup and history-cardinality work. [Agent source](https://github.com/henrygd/beszel/tree/v0.21.1/agent), [system entities](https://github.com/henrygd/beszel/tree/v0.21.1/internal/entities/system).

## Proof gates before enablement

1. Build the exact Darwin agent package and pin the hub container, validate CLI names/flags, and prove the services start after reboot without a GUI login. Confirm state/log ownership, bounded logs and automatic restart.
2. Prove browser Access enforcement, matching-email header login, denied spoofed header from other origin peers, and superuser recovery. Confirm whether cloudflared is local or remote before choosing bind addresses and proxy allowlist.
3. Prove hub-to-agent connections from inside the services VM/container over Tailscale only (host SSH reachability is insufficient), firewall/tailnet denial from other peers, agent recovery after sleep/network changes, and expected MacBook-offline behavior.
4. Check host graphs against native tools under idle and one representative build. Do not claim missing optional Darwin values as measured zero.
5. Use local hub `/api/health` and `beszel health --url …`; `beszel-agent health` checks a heartbeat file and does **not** establish successful hub ingestion. Confirm both systems' timestamps in the hub. Use an external heartbeat service only if hub-down alerts are desired; a hub cannot notify while it is offline. [Health checks](https://beszel.dev/guide/healthchecks), [agent implementation](https://github.com/henrygd/beszel/blob/v0.21.1/agent/health/health.go).
6. Restore an off-host backup into an isolated hub and verify users, history, identity key and subsequent agent reconnect before considering recovery complete.

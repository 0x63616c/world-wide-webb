# Tart 2.41.1 URLSession disk-layer failure: narrow source findings

Research performed 2026-11-07; no runner host operations, credential access, or configuration changes. Public Apple docs and Tart source/issues only. This note does not identify a confirmed root cause.

## Evidence supplied by the primary agent

The actual UID 451 system LaunchDaemon has SessionCreate enabled and the intended HOME/working directory. Tart's public GHCR manifest request succeeds, but disk-layer requests fail repeatedly with the offline description and ultimately exit 1. Curl under the same UID can receive an authenticated anonymous blob Range 0–0 response 206; the primary agent retains all authentication input privately. Targeted CFNetwork logs show a repeated CDN hostname hash failing DNS/path establishment in about 1 ms with an unsatisfied “No network route” path, without an explicit policy-denial message. The hostname and full nested NSError are not available in this research.

These are reported observations, not independently reproduced by this research. They establish a difference between request paths, not a diagnosed audit-session, DNS, VPN, local-network privacy, or URLSession defect.

### Subsequent primary-agent observation

After the failed Tart process exited, a fresh Tart process launched through the same LaunchDaemon began downloading disk layers and passed 10% progress without any configuration change. A native curl probe launched as UID 451 through the same LaunchDaemon and audit context also reached the CDN host and received HTTP 400. This unblocks the download attempt and makes a transient cached path state plausible, but neither the exact cause nor a reliable remedy has been established. These observations do not justify changing host networking or security settings.

## Source facts that constrain the diagnosis

Inspected local official clone using `git show 2.41.1:<path>`, rather than HEAD. Tag resolves to `543453404cd1b15c1338b6b70e162d000c8ba5e2`; local main resolves to `c20da4f9bea82ed4794144c6c753c4d66066663b`.

- [Fetcher.swift at 2.41.1](https://github.com/cirruslabs/tart/blob/2.41.1/Sources/tart/Fetcher.swift): one fileprivate URLSession uses `URLSessionConfiguration.default`; only explicit configuration change is disabling automatic cookies. Every fetch unconditionally creates `urlSession.dataTask(with: request)`. The `viaFile` argument is unused. There is no background configuration or URLSessionDownloadTask distinction between manifests and disk layers. `git diff 2.41.1 main -- Sources/tart/Fetcher.swift` is empty in this clone.
- [Registry.swift at 2.41.1](https://github.com/cirruslabs/tart/blob/2.41.1/Sources/tart/OCI/Registry.swift): pullManifest uses dataRequest, while pullBlob uses channelRequest with viaFile:true; both reach the same Fetcher. Blob initially sends no Range header; Range `bytes=<offset>-` is sent only after some bytes were delivered and a retry resumes. Manifest adds its OCI Accept header. Both share User-Agent and bearer authentication handling. Fetcher has no custom redirection delegate, connectivity settings, proxy configuration, or HTTP/3 override.
- [DiskV2.swift at 2.41.1](https://github.com/cirruslabs/tart/blob/2.41.1/Sources/tart/OCI/Layerizer/DiskV2.swift): disk layers are fetched concurrently through a task group constrained by the supplied concurrency; each layer gets up to five attempts for URLError. The retry log prints only `localizedDescription`, hiding NSError.userInfo and underlying errors. Same generic message across retries therefore cannot establish the underlying failure mechanism. Fetcher itself forwards original errors into the response continuation/stream.
- `git grep` across Sources/tart at tag found no `assumesHTTP3Capable`, waitsForConnectivity, allowsConstrainedNetworkAccess, allowsExpensiveNetworkAccess, connectionProxyDictionary, didFinishCollecting metrics, or willPerformHTTPRedirection implementation. Public GHCR blob redirects, negotiated protocols and resolved endpoints remain unobserved in the supplied evidence; do not assume them identical to manifest requests.

## Apple documentation and relevant upstream issue

1. [Apple waitsForConnectivity](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/waitsforconnectivity): when connectivity is unavailable and waiting is false, URLSession can fail immediately with NSURLErrorNotConnectedToInternet. Apple gives policy/configuration examples including disabled cellular and missing required VPN. This property applies to connection establishment; background sessions always wait. This supports examining connection policy/path details; it does not prove physical network outage or justify an untested waitsForConnectivity fix.
2. [Apple CFNetwork diagnostic logging](https://developer.apple.com/documentation/network/debugging-https-problems-with-cfnetwork-diagnostic-logging): CFNETWORK_DIAGNOSTICS accepts levels 0–3 and must be set before Foundation networking initializes. Apple directs macOS investigation to Console or sysdiagnose. These logs expose internal request state and may include decrypted sensitive traffic. If collected by the primary agent, restrict access and redact tokens, Authorization headers and signed URL query values before retaining/sharing. No logs were enabled in this research.
3. [Apple TN3179, macOS considerations](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy#macOS-considerations): macOS automatically permits local network access for launchd daemons, root programs, and CLI tools launched from Terminal/SSH and their children. Agents are excluded from the daemon exemption. The permission concerns directly connected local network addresses, multicast/broadcast, and local-name operations; ordinary public Internet addresses are outside that definition. Thus a true system LaunchDaemon fetching public GHCR is not explained by a blanket non-admin local-network restriction. Actual resolved/redirected endpoint evidence still matters.
4. [Tart issue #1056](https://github.com/cirruslabs/tart/issues/1056) (redirects to official current openai/tart repository): reports headless SSH Tart 2.24.1 failing against a **local registry**, while curl succeeds. NSError contains underlying CFNetwork -1009, POSIX stream code 50, and a satisfied NWPath. Reporter confirmed GUI Local Network approval resolved that specific case. Maintainer later cites usage-description packaging beginning 2.25.0. This is useful proof that curl success and -1009 can coexist with policy denial, but its local-registry/older-version circumstances do not establish this runner's cause.
5. [Apple assumesHTTP3Capable](https://developer.apple.com/documentation/foundation/urlrequest/assumeshttp3capable): the request hint enables QUIC racing without discovery when true; current documented default false (Apple reserves possible future change). Tart does not set it. No evidence here supports prescribing an HTTP/3 disable switch.
6. [Apple transaction metrics networkProtocolName](https://developer.apple.com/documentation/foundation/urlsessiontasktransactionmetrics/networkprotocolname): reports the protocol used to fetch a resource, e.g. h2 or http/1.1, including tunnel semantics. A diagnostic probe could record protocol and transaction URL/redirect sequence without changing production security policy. Tart has no metric delegate at this tag.

## Most discriminating next evidence (recommendation, not executed)

Capture a minimal Foundation URLSession dataTask request under the same effective UID and launchd context, first against the manifest and then the exact initial blob URL, recording full NSError domain/code/userInfo recursively with signed queries and headers removed. Retain `_NSURLErrorNWPathKey`, `_kCFStreamErrorDomainKey`, `_kCFStreamErrorCodeKey`, underlying errors, failing URL host, task type, timing, and whether headers/bytes arrived. These underscore keys are diagnostic observations, not stable public API contracts. Record redirect host/endpoint family and protocol through task delegates/metrics if a purpose-built probe is authorized. Compare full GET behavior with curl's existing Range 0–0 success; that tiny-range result does not test the same response body or execution stack.

I found no primary-source evidence establishing that service UID 451, HOME=/var/lib/_runner, SessionCreate=true, or absence of GUI login by itself causes this exact manifest-success/disk-failure behavior. Avoid changing user privilege, local-network security defaults, proxies, or HTTP protocols on that inference.

An [Apple Developer Forums report with a similar immediate unsatisfied path](https://developer.apple.com/forums/thread/782986) concerned a transparent-proxy Network Extension and broader system connectivity failure. Apple DTS recommended comparing affected and bypassed flows and reducing interacting network extensions before filing a focused bug. That is an example of the same log vocabulary having another cause; it supplies no supported fix for this daemon and does not establish that this host has the reported proxy condition.
